## 1. KNOWN EXPLOITED -- [CVE-2025-39682](https://nvd.nist.gov/vuln/detail/CVE-2025-39682)  
`KNOWN EXPLOITED` `CRITICAL` `CVSS 9.8` `published 2025-09-05`

> **KNOWN EXPLOITED.** CISA lists this as known-exploited in Linux Kernel on 2026-09-18, so it is being used against people now -- that outranks severity.

**What happened:** In the Linux kernel, the following vulnerability has been resolved: tls: fix handling of zero-length records on the rx_list Each recvmsg() call must process either - only contiguous DATA records (any number of them) - one non-DATA record If the next record has different type than what has already been processed we break out of the main processing loop. If the record has already been decrypted (which may be the case for TLS 1.3 where we don't know type until decryption) we queue the pending record to the rx_list. Next recvmsg() will pick it up from there. Queuing the skb to rx_list after zero-copy decrypt is not possible, since in that case we decrypted directly to the user space buffer, and we don't have an skb to queue (darg.skb points to the ciphertext skb for access to metadata like length). Only data records are allowed zero-copy, and we break the processing loop after each non-data record. So we should never zero-copy and then find out that the record type has changed. The corner case we missed is when the initial record comes from rx_list, and it's zero length.

**Who is affected:** Affected products per NVD: Linux, Siemens SIMATIC CN 4100, linux linux kernel, debian debian linux, siemens simatic cn 4100 firmware, siemens simatic cn 4100.

**How serious:** CRITICAL (CVSS 9.8, v3.1). Critical -- treat as urgent. Vector: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H.

## 4. KNOWN EXPLOITED -- [CVE-2026-53266](https://nvd.nist.gov/vuln/detail/CVE-2026-53266)  
`KNOWN EXPLOITED` `HIGH` `CVSS 8.8` `published 2026-06-25`

> **KNOWN EXPLOITED.** CISA lists this as known-exploited in Linux Kernel on 2026-09-18, so it is being used against people now -- that outranks severity.

**What happened:** In the Linux kernel, the following vulnerability has been resolved: netfilter: bridge: make ebt_snat ARP rewrite writable The ebtables SNAT target keeps the Ethernet source address rewrite behind skb_ensure_writable(skb, 0). This is intentional: at the bridge ebtables hooks the Ethernet header is addressed through skb_mac_header()/eth_hdr(), while skb->data points at the Ethernet payload. Asking skb_ensure_writable() for ETH_HLEN bytes would check the payload, not the Ethernet header, and would reintroduce the small packet regression fixed by commit 63137bc5882a. However, the optional ARP sender hardware address rewrite is different. It writes through skb_store_bits() at an offset relative to skb->data: skb_store_bits(skb, sizeof(struct arphdr), info->mac, ETH_ALEN) skb_header_pointer() only safely reads the ARP header; it does not make the later sender hardware address range writable. If that range is still held in a nonlinear skb fragment backed by a splice-imported file page, skb_store_bits() maps the frag page and copies the new MAC address directly into it. Ensure the ARP SHA range is writable before reading the ARP header and before calling skb_store_bits().

**Who is affected:** Affected products per NVD: Linux, linux linux kernel.

**How serious:** HIGH (CVSS 8.8, v3.1). High -- patch on the next maintenance window. Vector: CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H.
