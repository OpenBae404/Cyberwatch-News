# CyberWatch Newsletter -- software reach table
#
# THE NAMED FILE the ranker reads for tier ordering (see src/news_rank.py and
# the selection rule in Plans.md). Reach answers one question only: if this
# software breaks, how many readers of a general security newsletter are
# touched by it? It is NOT a profile, it is NOT one machine's inventory, and
# adding a line here must never be a way to smuggle "my homelab runs this"
# into an audience newsletter. If you cannot defend a line as "a lot of
# readers run this", it does not belong.
#
# FORMAT
#   <weight>  <token>[, <token>...]    # trailing comment optional
#   weight  0-100, higher = more readers affected
#   token   a product, a vendor or a brand -- see the two sections below
#
#   Several tokens on ONE line are spellings of ONE reach claim: "edge,
#   microsoft edge", "log4j, log4j2", "iphone os, apple/ios". They share the
#   line because they share the weight. Every weight in this file is the
#   ranker's tie-break scale and was argued for elsewhere; a change to HOW
#   tokens match adds spellings to existing weights and never invents a new
#   one, so the weight column of this file is diff-proof.
#
# HOW A PRODUCT TOKEN MATCHES
#   Case-insensitively, against the PRODUCT names the feed states for an item,
#   from the START of the name at a word boundary. "windows" matches "Windows
#   Server 2019" and "exchange" matches "Exchange Server", because a product
#   name is written head-first: the software, then the edition or platform.
#   Two things are refused:
#     * a word in the MIDDLE -- "Fortinet FortiPAM Chrome Extension" is a
#       FortiPAM thing, not Chrome, and scoring it 98 as "chrome" is one of
#       the two defects this rule replaces;
#     * a match that stops inside a word -- "Net-IDN-Encode" is a Perl module
#       and not Microsoft ".NET", "nginx-ignition" is not nginx. A hyphen or a
#       dot binds; a space, an underscore, a comma, a slash or a pipe
#       separates, so "internet_explorer" and "iOS, iPadOS, and macOS" still
#       read as lists of words.
#   A token may also be written "vendor product" ("google chrome", "linux
#   kernel") and then matches the vendor-qualified spelling of the name.
#
# A COMPANY IS NOT SOFTWARE -- vendor:, brand: and <vendor>/<product>
#   "cisco" as a plain token would lead every product name Cisco ships, so a
#   Cisco IP camera would carry IOS's 60. That is the same over-reach one
#   level up, and it is why every company in this file is written one of two
#   ways. The test is one question: if this token may lead a product name, is
#   the weight honest for EVERY name it can lead?
#
#     vendor:<name>   No -- the catalogue runs from the core of the internet
#                     down to a webcam. It then scores ONLY a row that names
#                     no product at all ("Apple / Multiple Products", 53 rows
#                     in the live CISA KEV catalogue) -- real, very wide items
#                     that would otherwise be unrated. It never scores a named
#                     product, so "Red Hat Build of Keycloak" is not 79 and
#                     "Fortinet FortiWeb Cloud Connector" is not 62.
#
#     brand:<name>    Yes, because the weight is already set at the level of
#                     the vendor's WEAKEST product. It then scores every row
#                     that vendor files, named or not, so a router model this
#                     table has never heard of still scores. "d-link" is 26
#                     because one household runs each piece of D-Link kit and
#                     that is true of every D-Link box. "cisco" can never be a
#                     brand: 60 is IOS-scale and a Cisco webcam is not.
#
#     <vendor>/<name> A product token that only means this software under this
#                     vendor. Cisco IOS is a router OS and Apple iOS is a
#                     phone OS; an unscoped "ios" hands every row of one to
#                     the other's weight.
#
#   A named product that is not listed here scores 0 -- UNRATED, not zero
#   reach. Some genuinely wide software is in that position today (Tomcat and
#   Struts under vendor:apache, Thunderbird under vendor:mozilla): they used
#   to score their vendor's weight through the old substring rule, which was
#   never a measurement of them. Naming them costs a weight this file cannot
#   invent under a matching change, so it is a table decision, not this one.
#
# A CVE scores the highest weight of any token it matches. No match scores 0 --
# unknown reach, not zero reach, and it only ever loses a tie.
#
# Lines starting with # and blank lines are ignored.
